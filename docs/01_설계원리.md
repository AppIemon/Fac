# 설계 원리 (모든 팜은 이 5단계로 분해된다)

```
산출원(source) → 이송(transport) → 처리(process) → 수거(collect) → 저장(store)
```

이 5칸만 채우면 어떤 팜이든 설계할 수 있다. 100개 카탈로그도 전부 이 분해를 따른다.
`engine/principle.py` 가 이 5칸을 읽어 아키타입과 치수를 확정한다.

---

## 1. 산출원 (source)

| 유형 | 무엇이 산출을 결정하는가 | 대표 팜 |
|---|---|---|
| `natural_spawn` | **어두운 면적** x 몹캡 독점률 | 일반 몹 트랩, 크리퍼 팜 |
| `spawner` | 활성 거리(16블록) 안에 플레이어가 있는가 | 좀비/스켈레톤 스포너 팜 |
| `structure_spawn` | **구조물 경계 좌표** (밖에서는 스폰 0) | 위더 스켈레톤, 마녀 오두막, 가디언 |
| `growth_column` | 포기 수 x 랜덤틱 | 사탕수수, 대나무, 선인장 |
| `growth_farmland` | 경작지 칸 수 x 랜덤틱 | 밀/당근/감자 |
| `breeding` | 성체 쌍 수 | 소/돼지/닭 |
| `villager` | 주민 수 + 침대/일자리 블록 | 철 팜, 거래소, 습격 팜 |
| `generation` | 생성-파괴 사이클 속도 | 조약돌/현무암/얼음 |
| `bartering` | 금괴 투입량 | 피글린 물물교환 |

### 자연 스폰의 3대 조건 (하나라도 어기면 산출이 0이 된다)
1. **블록광 0** — 1.18 이후 적대 몹은 블록광 0에서만 스폰한다. 하늘광은 무관.
2. **플레이어로부터 24블록 이상** — 그 안에서는 스폰 자체가 없다.
3. **몹캡 독점** — 몹캡은 플레이어당 70마리(적대). 주변 동굴이 이걸 나눠 먹으면
   팜 효율이 1/10로 떨어진다. **팜 성능의 90%는 "주변 스폰 차단"에서 나온다.**

### 거리 3종 세트
| 거리 | 의미 |
|---|---|
| 24블록 | 이 안에서는 스폰 안 함 → AFK 지점을 여기 밖에 |
| 32블록 | 이 밖에서는 확률적 소멸 시작 |
| 128블록 | 이 밖은 즉시 소멸 → 팜 전체가 이 반경 안에 들어와야 함 |

## 2. 이송 (transport)

| 방식 | 조건 |
|---|---|
| `water` | **오버월드/엔드 전용.** 네더에서는 물이 즉시 증발한다 |
| `gravity` | 구멍만 뚫으면 됨. 가장 고장이 없다 |
| `piston` | 플라잉 머신/블록 밀기. 작물·블록 생성형에 필수 |
| `minecart` | 호퍼 미니카트. 넓은 면적을 한 줄로 훑을 때 |
| `mob_ai` | 유인체(엔더마이트/주민)로 몹을 스스로 걸어오게 함 |

**물길 상수**: 수원 1개는 평지로 **7블록**까지 흐른다(수원 포함 8칸).
그래서 물길은 8칸마다 수원을 다시 놓아야 끊기지 않는다. 엔진이 자동으로 배치한다.

---

## 3. 처리 (process)

### 낙하 데미지
```
데미지 = floor(낙하거리) - 3
```

| 목적 | 체력 20 몹(좀비/스켈레톤/크리퍼) 기준 |
|---|---|
| 즉사 | **23블록** |
| 1HP만 남기기(직접 타격 → 경험치/드롭 증가) | **22블록** |

체력이 높은 몹은 표를 다시 계산해야 한다. 엔진이 `MOB_HP` 를 보고 자동 계산한다.

**낙하가 통하지 않는 몹**: 블레이즈, 가스트, 셜커, 위더, 엔더 드래곤.
철 골렘은 체력 100이라 실용적이지 않다 → **용암 블레이드**를 쓴다.

### 그 외
- `observer_cut` — 관측기가 성장을 감지 → 피스톤이 즉시 절단. 기둥 작물의 표준.
- `piston_break` — 피스톤으로 밀어 블록을 파괴. 블록 생성형의 표준.
- `smelt` — 화로 1대 = **시간당 360개**. 그 이상은 화로를 늘려야 한다.

---

## 4. 수거 (collect)

- 호퍼 1개 처리량 = **초당 2.5개** (쿨다운 8틱). 이게 대부분 팜의 진짜 병목이다.
- 아이템은 **5분(300초)** 뒤 소멸한다. 그 안에 호퍼에 들어가야 한다.
- 산출이 초당 2.5개를 넘으면 호퍼 라인을 **병렬로 쪼개라.**

---

## 5. 저장 (store)

- 클래식 호퍼 분류기: 비교기가 필터 아이템 신호를 읽어 호퍼 잠금을 제어.
  필터 슬롯 = **필터 아이템 18개 + 스택 불가 아이템 4개**가 표준.
- 26.x 구리 골렘 분류기: 구리 상자에서 최대 16스택을 집어, **같은 아이템이 이미 든
  나무 상자**에만 넣는다. 빈 상자는 아무거나 받으므로 지정 아이템을 미리 넣어둘 것.
  느리므로 고속 팜에는 부적합.
- **오버플로 라인은 선택이 아니라 필수.** 상자가 차면 팜 전체가 멈춘다.

## 병목 계산 (이게 설계의 마지막 단계다)

전체 속도 = 5단계 중 **가장 느린 단계**. 순서대로 확인한다.

1. 산출원이 초당 몇 개를 뱉는가?
2. 이송이 그걸 다 받는가? (물길은 사실상 무제한, 미니카트는 아님)
3. 처리 속도가 유입을 따라가는가? (제련은 화로 수, 처치는 낙하 통로 폭)
4. 호퍼 라인이 감당하는가? (초당 2.5개 x 라인 수)
5. 상자가 차면 어떻게 되는가?

`python3 -m engine.cli facts` 로 위 수치를 언제든 확인할 수 있다.

## 산출량 추정식에 대한 주의

`spawn_rate_estimate()` 는 다음 모델을 쓴다.

```
시간당 몹 = 몹캡(70) x 독점률 x 면적포화도 x (3600 / 몹캡 회전주기 60초)
```

- **면적포화도**는 1500칸에서 1.0으로 막힌다. 그 이상 넓혀도 산출이 늘지 않는다.
  **몹캡이 병목이 되기 때문**이다. 플랫폼을 무한정 키우는 건 낭비다.
- 이 값은 잘 지은 범용 몹 트랩의 실측 범위(시간당 수천 마리)에 맞춘 **추정치**다.
  정확한 수치가 필요하면 인게임 실측으로 대체할 것.
- 그래서 **면적보다 "주변 스폰 차단"(독점률)이 훨씬 큰 변수**다.
  같은 팜이 바다 위에서 몇 배 더 잘 도는 이유가 이것이다.
